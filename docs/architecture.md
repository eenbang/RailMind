# RailMind 整体架构

## 1. 设计目标

RailMind 首版需要验证的核心命题是：

> 把“用户模糊的出行偏好”转化为“可解释、可调整、可比较的车次组合”。

因此架构优先保证四件事：

1. **输入统一**：表单和自然语言最终进入同一个 `TravelRequest`。
2. **数据可替换**：样例文本、SQLite、未来第三方数据源对上层透明。
3. **算法可解释**：推荐不是黑盒排序，每个结果都能说明得失。
4. **功能可拆分**：每条线路、每种交通方式或每种评分维度可以独立迭代。

## 2. 分层

```text
┌──────────────────────────────────────────────────────┐

└───────────────────────────┬──────────────────────────┘
                            │ use-case calls
┌───────────────────────────▼──────────────────────────┐
│ Application Services                                 │
│ Intent parsing / journey search / recommendation /   │
│ explanation assembly                                 │
└──────────────┬───────────────────────────┬───────────┘
               │                           │
┌──────────────▼─────────────┐ ┌───────────▼───────────┐
│ Domain                     │ │ Ports / Adapters       │
│ request, journey, scoring  │ │ repository, LLM, clock │
└──────────────┬─────────────┘ └───────────┬───────────┘
               │                           │

```

依赖方向始终指向领域层。`domain/` 不导入 FastAPI、数据库驱动或 LLM SDK。

## 3. 核心数据流

```text
用户
 ├─ 表单输入 ───────────────┐
 └─ 自然语言输入 → 意图解析 ─┤
                             ▼
                    TravelRequest
                             │
                    标准化出行条件
                             │
                 JourneyRepository.search
                             │
        候选车次 → 硬性过滤 → 多目标评分
                             │
              推荐结果 + 分项得分 + 理由
                             │
      用户查看详情 / 比较 / 调整偏好滑块
                             │
                      重新计算推荐
```

调整偏好时重新运行评分，不重复调用 LLM。自然语言解析只在原始输入变化时执行。

## 4. 模块职责

### 前端

- `app/`：应用壳、路由、全局 Provider。
- `features/search/`：表单输入、自然语言输入、表单状态。
- `features/recommendations/`：推荐卡片、偏好控制台、方案对比、解释展示。
- `services/`：HTTP 客户端，不包含业务计算。
- `types/`：与 API 契约对齐的传输类型。

前端不自行复制推荐算法。拖动滑块只修改权重，然后请求后端重新评分，确保表单、AI 和后续客户端得到相同结果。

### API 层

- 校验请求和响应结构。
- 把传输模型转换为领域模型。
- 处理 HTTP 状态码、错误映射和依赖注入。
- 不直接读取文本文件，也不包含评分公式。

### 应用服务层

- `JourneySearchService`：标准化查询并获取候选车次。第一版先使用内置数据库，后续考虑增加内置数据库的列车数量或直接调用12306官方API。
- `RecommendationService`：应用硬过滤、调用评分器、组装解释。
- `IntentParser`：将自然语言转换为未补全的 `TravelRequest`。
- `ClarificationPolicy`：决定哪些字段必须反问、哪些可以安全使用默认值。

### 领域层

- `TrainJourney`：不可变的单条车次及其票价信息。
- `TravelRequest`：一次推荐的完整输入。
- `PreferenceWeights`：价格、时长、舒适性、时间合适度的权重。
- `Recommendation`：候选车次、总分、分项分数、推荐理由和取舍。
- 评分器：纯函数或纯对象，便于单元测试和离线评估。
该评分器具体要如何实现？不能让AI自由发挥，否则不一定能保证效果。

### 适配器

- `TextJourneyRepository`：当前样例数据解析，便于立即开发界面。
- `SqliteJourneyRepository`：后续正式查询和索引。
- `RuleBasedIntentParser`：无密钥、可预测的回退方案。
- `LlmIntentParser`：在规则解析不足时接入结构化输出 LLM。
- `PurchaseLinkBuilder`：生成购票平台跳转信息，不直接处理支付。

## 5. 关键设计决策

### 两种输入共用一个需求模型

自然语言不是另一套查询链路。LLM 只负责抽取和补全 `TravelRequest`，推荐仍由确定性业务逻辑完成。这能降低成本、提高可测试性，也避免不同入口给出不同结果。

### 规则优先，LLM 增强

上海、杭州、时间窗口、预算和座位类型都有稳定表达，基础规则即可覆盖大部分控制台演示。LLM 用于处理复合句、省略和口语化偏好，并输出结构化 JSON。LLM 不可用时自动回退到规则解析。

### 先过滤，再评分

- 硬性条件：旅途首末站、日期、预算上限、最长耗时、指定出发时间段、座位可得性。
- 软偏好：价格更低、时间更短、舒适性更高、时间更合适。

软偏好只影响排序，不静默删除候选。若硬过滤后结果为空，返回可放宽条件的建议。

### 推荐理由由数据生成

解释不是自由生成文案。服务根据得分差、相对排名和明确字段组装理由，例如“比平均票价低 32 元”“全程仅多 9 分钟”。后续可让 LLM 润色，但事实来源仍是结构化比较结果。

### 舒适性独立计分

首版根据车次类型、座位等级、是否夜间和换乘次数形成基础分。数据不足时返回较低置信度，不把推断包装成确定事实。

## 6. 扩展点

| 未来能力 | 主要落点 | 是否改变主流程 |
|---|---|---|
| SQLite / 全国线路 | 新增 Repository 实现 | 否 |
| 实时余票 | 新增 Availability Adapter | 否 |
| LLM 自然语言 | 实现 IntentParser | 否 |
| 中转规划 | 新增 RoutePlanner 服务 | 增加查询阶段 |
| 用户偏好学习 | 新增 Profile Repository | 否 |
| 账号与收藏 | 新增 Auth/User 模块 | 不影响领域核心 |
| 多交通方式 | 抽象 TransportOption | 需要领域升级 |
| 购票跳转 | PurchaseLinkBuilder | 否 |

## 7. 非功能边界

- **可解释性**：推荐结果必须带分项分数和理由。
- **确定性**：同一数据、同一请求、同一算法版本应得到相同排序。
- **可追踪性**：保存请求、算法版本、数据版本和最终排序，便于排查。
- **隐私**：首版不保存身份信息；日志不得记录完整自然语言原文，除非明确开启调试。
- **降级**：LLM、第三方余票或地理服务失败时，传统表单与本地样例查询仍可用。


## 8. 数据库数据结构

- 我们得想想数据库里的具体数据结构，该收集哪些数据，数据库要提供哪些数据，哪些数据可以从12306上联网查询，哪些数据查不到，只能内置在本地数据库。
- 比如车次信息、票价、列车型号(普速除外，考虑从路路通上获取普速的型号，也可从车次头反推默认车型)、到发时间、到发站等可以直接从12306查询，而列车插座位置、座位分布、普速是否禁烟、列车座椅舒适度、列车环境舒适度、列车停靠站台号等信息可能就要本地存储在数据库中。
