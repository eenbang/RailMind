# RailMind 产品范围

## 用户问题

用户选择火车时通常不是只追求最低价，而是在票价、用时、出发时间、舒适度和到达便利性之间权衡。传统查询工具给出完整列表，但用户仍需自行比较；RailMind 的任务是把这些取舍显式化。

## 第一版用户旅程

```text
进入 RailMind
  → 选择表单或自然语言
  → 确认上海到杭州的出行条件
  → 获得默认的 3 个推荐方案
  → 查看推荐理由与分项得分
  → 调整偏好滑块或排除条件
  → 结果实时重排
  → 比较 2–3 个方案
  → 前往外部购票平台
```

## 第一版范围

### 必须完成

- 上海至杭州的传统表单查询
- 车次类型、出发时段、价格、耗时等基础过滤
- 自然语言输入的统一入口
- 多目标评分与默认推荐
- 价格、时间、舒适性、时间合适度偏好控制
- 推荐理由与取舍说明
- 2–3 个方案的并列比较
- 响应式桌面与移动端布局

### 允许使用简化实现

- 自然语言先用规则解析，预留 LLM 接口
- 车次从本地文本加载，后续再迁 SQLite
- 舒适度为启发式评分，并标注为估算
- 日期只进入需求模型，样例数据暂不区分类别
- 购票按钮只生成搜索入口，不处理支付

### 明确不在第一版

- 全国线路覆盖
- 真实实时余票
- 智能中转组合
- 动态票价预测
- 用户画像与个性化学习
- 登录、订单、支付、退改签
- 原生移动应用

## 信息架构

| 页面/区域 | 用户目标 | 首版内容 |
|---|---|---|
| 首页/出行规划 | 描述需求 | 表单、自然语言输入、默认条件 |
| 推荐结果 | 快速选择 | 默认推荐、Top 3、推荐理由 |
| 偏好控制台 | 调整取舍 | 四个权重滑块、预算和时长上限 |
| 方案详情 | 判断合适度 | 车次信息、票价、评分构成、购票入口 |
| 方案对比 | 消除犹豫 | 关键字段横向对比、最优项高亮 |

## 默认产品策略

- 默认出发时间：08:00–12:00。
- 默认权重：价格 30%、耗时 35%、舒适性 20%、时间合适度 15%。
- 默认展示 3 个方案，但允许查看全部候选。
- 时间范围、座位和预算属于硬条件；偏好权重属于软条件。
- 自然语言未提供线路时，先追问起终点；日期等非关键字段可暂用“未指定”。
- 结果为空时，明确列出冲突条件并提供一键放宽。

## 成功标准

框架阶段用以下标准判断是否可继续开发：

1. 表单与自然语言能产出同一结构的需求对象。
2. 替换数据源不需要修改页面或推荐服务。
3. 调整一个偏好后，推荐排序变化有可解释原因。
4. 每个推荐结果能指出优点、代价和相对比较对象。
5. 后续添加中转、余票或账号时，不需要重写基础出行流程。
